Introduction to Databases & DBMS

From file-based chaos to organized, persistent, shared data managed by a DBMS.

1.1 What Is a Database?

A database is an organized (defined structure), persistent (survives after program stops), collection of related (meaningfully connected) data that models some aspect of the real world.

1.5 Three-Level Architecture (ANSI/SPARC 1975)

┌────────────────────────────────────────────┐
│  EXTERNAL LEVEL (User Views)               │  ← Student sees own grades only
│  What individual users / apps see          │     Finance sees tuition, not grades
├────────────────────────────────────────────┤
│  CONCEPTUAL LEVEL (Logical Schema)         │  ← All tables, columns, FK relationships
│  Full logical picture of the entire DB     │     All business constraints
├────────────────────────────────────────────┤
│  INTERNAL LEVEL (Physical Storage)         │  ← B+Tree index files, 16KB pages
│  How data is physically stored on disk     │     Compression format, file locations
└────────────────────────────────────────────┘

Physical Data Independence: Change how data is stored (add index, change page size) → no application code changes needed.

Logical Data Independence: Add new tables or columns → existing application views still work. Harder to achieve.

2.3 Cardinality Constraints

TypeDefinitionExampleSQL Approach
1:1Each A → at most one B, each B → at most one AEmployee — OfficeFK on total-participation side
1:NOne A → many Bs; each B → exactly one ADepartment → StudentsFK (dept_id) goes in STUDENT table
M:NMany A → many BStudent ↔ CourseJunction table ENROLLMENT with FKs to both
KEY RULE: A M:N relationship CANNOT be represented with just two tables. You MUST create a third junction table containing the PKs of both entities as FKs. Relationship attributes (grade, semester, status) become columns in this junction table.

2.4 Seven ER-to-Relational Mapping Rules

RULE 1 — STRONG ENTITY

Each strong entity → table. Key attribute → PK. Composite → separate columns. Omit derived attributes (compute at query time).

RULE 2 — WEAK ENTITY

Weak entity → table. Include partial key + owner's PK = composite PK. Add FK referencing the owner entity with CASCADE delete.

RULE 3 — 1:1 RELATIONSHIP

Add PK of one entity as FK in the other. Prefer total-participation side to receive the FK. Or merge both if always present together.

RULE 4 — 1:N RELATIONSHIP

Add PK of the "one" side as FK in the "many" side table. No separate table needed. Example: dept_id FK goes in STUDENT.

RULE 5 — M:N RELATIONSHIP

Create new junction table with PKs of both entities as FKs. These form the PK (or add surrogate PK). All relationship attributes → columns.

RULE 6 — MULTI-VALUED ATTRIBUTE

New table: entity FK + attribute value. PK = (entity FK + value). Example: STUDENT_PHONE(student_id FK, phone_number)

2.5 University Schema (After Mapping)

-- Rule 1: Strong entities → tables
DEPARTMENT  (dept_id PK, name, code, head_name, location)
STUDENT     (student_id PK, s_code, first_name, last_name, email, gpa, enroll_year, status)
COURSE      (course_id PK, code, title, credit_hours, max_students)
PROFESSOR   (prof_id PK, name, email, rank)

-- Rule 4: 1:N relationships → FK on the "many" side
STUDENT.dept_id    FK → DEPARTMENT.dept_id

-- Rule 5: M:N relationship → junction table
ENROLLMENT  (enroll_id PK, student_id FK, course_id FK, semester, year, grade, status)

-- Rule 6: Multi-valued attribute → separate table
STUDENT_PHONE  (student_id FK, phone_number)  PK = (student_id, phone_number)

3.2 Key Type Hierarchy

SUPERKEY (any set of attributes that uniquely identifies rows — may be redundant)
    ↓  minimal: remove any attribute → no longer unique
CANDIDATE KEY (minimal superkey — multiple can exist per table)
    ↓  designer picks ONE
PRIMARY KEY ← chosen as official identifier — NEVER NULL, always UNIQUE
    ↓  remaining candidate keys
ALTERNATE KEYS → enforced with UNIQUE constraint
Example on STUDENT(student_id, national_id, email, first_name, dept_id):
Superkeys: {student_id}, {national_id}, {email}, {student_id, national_id}, ...
Candidate Keys: {student_id}, {national_id}, {email}
Primary Key: student_id (surrogate — always available, never null)
Alternate Keys: national_id (UNIQUE), email (UNIQUE)

3.5 NULL Values — Critical Rules

-- NULL arithmetic: any operation involving NULL returns NULL
SELECT 5 + NULL;        -- Result: NULL (not 5!)
SELECT 100 * NULL;      -- Result: NULL

-- NULL comparison → UNKNOWN (not TRUE or FALSE)
SELECT NULL = NULL;    -- UNKNOWN (not TRUE!)
SELECT NULL <> NULL;   -- UNKNOWN (not FALSE!)

-- CORRECT ways to test for NULL
SELECT * FROM students WHERE phone IS NULL;      -- ✓ CORRECT
SELECT * FROM students WHERE phone IS NOT NULL;  -- ✓ CORRECT
SELECT * FROM students WHERE phone = NULL;       -- ✗ WRONG: always 0 rows

-- Aggregate functions and NULL
COUNT(*)          -- counts ALL rows including NULLs
COUNT(grade)      -- counts ONLY rows where grade IS NOT NULL
AVG(grade)        -- NULLs excluded from average
SUM(grade)        -- NULLs excluded from sum

4.3 Complete University DDL

-- Create database
CREATE DATABASE IF NOT EXISTS university
    CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
USE university;

-- DEPARTMENT (no FK — create first)
CREATE TABLE departments (
    dept_id    INT           NOT NULL AUTO_INCREMENT,
    name       VARCHAR(100) NOT NULL,
    code       CHAR(5)       NOT NULL,
    head_name  VARCHAR(100) DEFAULT NULL,
    created_at TIMESTAMP     DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT pk_dept      PRIMARY KEY (dept_id),
    CONSTRAINT uq_dept_code UNIQUE (code)
);

-- STUDENT (references DEPARTMENT)
CREATE TABLE students (
    student_id  INT           NOT NULL AUTO_INCREMENT,
    s_code      VARCHAR(20)  NOT NULL,
    first_name  VARCHAR(50)  NOT NULL,
    last_name   VARCHAR(50)  NOT NULL,
    email       VARCHAR(150) NOT NULL,
    gpa         DECIMAL(3,2) NOT NULL DEFAULT 0.00,
    dept_id     INT           NOT NULL,
    enroll_year YEAR          NOT NULL,
    status      ENUM('active','inactive','graduated') NOT NULL DEFAULT 'active',
    CONSTRAINT pk_students     PRIMARY KEY (student_id),
    CONSTRAINT uq_s_code       UNIQUE (s_code),
    CONSTRAINT uq_email        UNIQUE (email),
    CONSTRAINT chk_gpa         CHECK (gpa BETWEEN 0.00 AND 4.00),
    CONSTRAINT fk_student_dept FOREIGN KEY (dept_id)
        REFERENCES departments(dept_id) ON DELETE RESTRICT
);

-- ENROLLMENT (junction table for M:N)
CREATE TABLE enrollments (
    enroll_id  INT          NOT NULL AUTO_INCREMENT,
    student_id INT          NOT NULL,
    course_id  INT          NOT NULL,
    semester   VARCHAR(20) NOT NULL,
    year       YEAR         NOT NULL,
    grade      DECIMAL(4,2) DEFAULT NULL,
    status     ENUM('enrolled','completed','dropped') NOT NULL DEFAULT 'enrolled',
    CONSTRAINT pk_enrollments    PRIMARY KEY (enroll_id),
    CONSTRAINT uq_enrollment     UNIQUE (student_id, course_id, semester, year),
    CONSTRAINT chk_grade         CHECK (grade BETWEEN 0 AND 100),
    CONSTRAINT fk_enroll_student FOREIGN KEY (student_id)
        REFERENCES students(student_id) ON DELETE CASCADE,
    CONSTRAINT fk_enroll_course  FOREIGN KEY (course_id)
        REFERENCES courses(course_id) ON DELETE RESTRICT
);

4.6 DML — INSERT, UPDATE, SELECT

-- Multi-row INSERT (one round trip)
INSERT INTO departments (name, code, head_name) VALUES
    ('Computer Science',    'CS',  'Dr. Amina Hassan'),
    ('Information Systems',  'IS',  'Dr. Khaled Omar'),
    ('Artificial Intelligence','AI', 'Dr. Sara Nabil');

-- BEST PRACTICE: run SELECT first, then UPDATE
SELECT * FROM students WHERE student_id = 5;  -- verify first
UPDATE students
    SET gpa = 3.75, status = 'active'
    WHERE student_id = 5;

-- Safe mode (prevents accidental full-table updates)
SET SQL_SAFE_UPDATES = 1;

-- SELECT with WHERE, ORDER BY, LIMIT, OFFSET
SELECT first_name, last_name, gpa
FROM students
WHERE status = 'active' AND gpa BETWEEN 2.5 AND 4.0
ORDER BY gpa DESC, last_name ASC
LIMIT 20 OFFSET 40;    -- page 3 (records 41-60)

-- LIKE patterns
WHERE last_name  LIKE 'Al%'       -- starts with Al
WHERE email      LIKE '%@uni.edu'  -- ends with @uni.edu
WHERE first_name LIKE '____'       -- exactly 4 characters long

-- IN and BETWEEN
WHERE dept_id IN (1, 2, 3)
WHERE gpa BETWEEN 3.0 AND 4.0    -- inclusive on both ends

-- INSERT from SELECT (archive graduated students)
INSERT INTO archive_students (student_id, full_name, email, archived_at)
    SELECT student_id, CONCAT(first_name, ' ', last_name), email, NOW()
    FROM students WHERE status = 'graduated';

4.7 SQL Logical Execution Order

1. FROM       → identify source tables, perform JOINs
2. WHERE      → filter individual rows (before aggregation)
3. GROUP BY   → group rows into aggregation groups
4. HAVING     → filter groups (after aggregation)
5. SELECT     → choose columns, compute expressions, aliases
6. DISTINCT   → remove duplicate result rows
7. ORDER BY   → sort the result set
8. LIMIT      → restrict row count / paginate
Why you CANNOT use a SELECT alias in WHERE: SELECT (step 5) runs AFTER WHERE (step 2). The alias doesn't exist yet when WHERE is evaluated. Use the full expression in WHERE, or wrap in a subquery.

JOIN Operations — The Heart of SQL

JOINs combine rows from two or more tables based on a related column — the fundamental operation of relational databases.

5.1.1 JOIN Types Overview

INNER JOIN
Only rows with a match in BOTH tables. Unmatched rows from either table are excluded.
LEFT JOIN
ALL rows from left table + matching right rows. NULL in right columns when no match.
RIGHT JOIN
ALL rows from right table + matching left rows. NULL in left columns when no match.
CROSS JOIN
Every combination of rows (Cartesian Product). n × m rows. Always use with LIMIT.
SELF JOIN
Table joined with itself using two aliases. Finds relationships within the same table.

5.1.2 INNER JOIN Examples

-- Students with their department name
SELECT
    s.s_code,
    CONCAT(s.first_name, ' ', s.last_name) AS student_name,
    s.gpa,
    d.name AS department
FROM students s
INNER JOIN departments d ON s.dept_id = d.dept_id
WHERE s.status = 'active'
ORDER BY s.gpa DESC;

-- Three-table JOIN: student + enrollment + course
SELECT
    s.first_name, s.last_name,
    c.code, c.title,
    e.semester, e.year, e.grade
FROM students s
JOIN enrollments e ON s.student_id = e.student_id
JOIN courses c     ON e.course_id  = c.course_id
WHERE e.status = 'completed'
ORDER BY s.last_name, c.code;

5.1.3 LEFT JOIN & Anti-Join Pattern

-- LEFT JOIN: all students, with or without enrollments
SELECT s.s_code, s.first_name, s.last_name, e.course_id, e.grade
FROM students s
LEFT JOIN enrollments e ON s.student_id = e.student_id
ORDER BY s.last_name;

-- ANTI-JOIN PATTERN: students NOT enrolled in any course
-- NULL in right-table column = no match found
SELECT s.s_code, s.first_name, s.last_name
FROM students s
LEFT JOIN enrollments e ON s.student_id = e.student_id
WHERE e.student_id IS NULL   -- ← key line: NULL means no enrollment found
ORDER BY s.last_name;

-- Departments with NO active students
SELECT d.name, d.code
FROM departments d
LEFT JOIN students s ON d.dept_id = s.dept_id AND s.status = 'active'
WHERE s.student_id IS NULL;
Anti-Join Pattern Summary:
1. LEFT JOIN both tables on the key relationship
2. Add WHERE right_table.id IS NULL
3. NULL means "no matching row was found in the right table"
→ Result: only rows from the left table that have NO match in the right table

5.1.4 SELF JOIN & CROSS JOIN

-- SELF JOIN: pairs of students in the same department
SELECT
    a.first_name AS student_a,
    b.first_name AS student_b,
    a.dept_id
FROM students a
JOIN students b
    ON  a.dept_id    = b.dept_id
    AND a.student_id < b.student_id  -- avoids duplicates AND self-match
ORDER BY a.dept_id, a.first_name;

-- CROSS JOIN: all student-course combinations (Cartesian Product)
SELECT s.s_code, c.code
FROM students s
CROSS JOIN courses c
WHERE s.dept_id = c.dept_id   -- always filter CROSS JOINs
LIMIT 100;                    -- always LIMIT CROSS JOINs

5.1.6 WHERE vs HAVING — Critical Difference

-- WHERE filters individual rows BEFORE aggregation
-- HAVING filters groups AFTER GROUP BY aggregation
SELECT
    dept_id,
    COUNT(*) AS student_count,
    AVG(gpa) AS avg_gpa
FROM students
WHERE  status = 'active'          -- step 2: filter rows BEFORE grouping
GROUP BY dept_id                   -- step 3: group rows
HAVING COUNT(*) > 5               -- step 4: filter groups AFTER aggregation
   AND AVG(gpa) >= 2.5
ORDER BY avg_gpa DESC;

5.1.7 Subqueries

-- Subquery in WHERE (scalar)
SELECT first_name, last_name, gpa
FROM students
WHERE gpa > (SELECT AVG(gpa) FROM students WHERE status = 'active');

-- Subquery with IN
SELECT first_name, last_name
FROM students
WHERE student_id IN (
    SELECT student_id FROM enrollments
    WHERE course_id = (SELECT course_id FROM courses WHERE code = 'DB201')
);

-- Derived table (subquery in FROM)
SELECT dept_name, dept_avg_gpa
FROM (
    SELECT d.name AS dept_name, ROUND(AVG(s.gpa), 2) AS dept_avg_gpa
    FROM departments d
    JOIN students s ON d.dept_id = s.dept_id
    WHERE s.status = 'active'
    GROUP BY d.dept_id, d.name
) AS dept_stats
WHERE dept_avg_gpa > (SELECT ROUND(AVG(gpa), 2) FROM students WHERE status = 'active')
ORDER BY dept_avg_gpa DESC;

-- EXISTS (often faster than IN for large tables)
SELECT first_name, last_name
FROM students s
WHERE EXISTS (
    SELECT 1 FROM enrollments e
    WHERE e.student_id = s.student_id AND e.grade > 90
);

Must-Know Rules for the Exam

Key Rules to Memorize

PRIMARY KEY

NEVER NULL. Always UNIQUE. Every table must have one. A NULL PK means "unknown identity" — impossible to reference.

FOREIGN KEY

Must match existing PK value or be NULL. dept_id=999 rejected if no dept 999 exists.

NULL VALUES

NULL ≠ 0 ≠ "" ≠ false → means UNKNOWN. NULL = NULL → UNKNOWN (not TRUE!). Always use IS NULL / IS NOT NULL.

FLOAT vs DECIMAL

FLOAT for money → WRONG. 0.1 + 0.2 = 0.30000000000000004. Always use DECIMAL for money and GPA.

M:N RELATIONSHIP

MUST create a junction table. Cannot represent M:N with just two tables. Relationship attributes go in the junction table.

DERIVED ATTRIBUTE

NOT stored in the database. Computed at query time. age (from birth_date) — dashed oval in Chen notation.

WHERE vs HAVING

WHERE filters rows BEFORE GROUP BY. HAVING filters groups AFTER GROUP BY. CANNOT use COUNT() in WHERE.

ANTI-JOIN PATTERN

LEFT JOIN + WHERE right.id IS NULL. Finds rows in left table with NO match in right table.

JOIN Patterns Cheat Sheet

-- Only matching rows
FROM A INNER JOIN B ON A.id = B.a_id

-- All A rows, including unmatched
FROM A LEFT JOIN B ON A.id = B.a_id

-- Find A rows with NO match in B (Anti-Join)
FROM A LEFT JOIN B ON A.id = B.a_id WHERE B.id IS NULL

-- Find pairs within same table (Self-Join)
FROM T a JOIN T b ON a.group_col = b.group_col AND a.id < b.id

-- Cartesian product (every combination)
FROM A CROSS JOIN B LIMIT 100
